# План доработки и расширения функционала проекта

## Стратегия развития
Развитие проекта разбито на 4 этапа (квартала) с постепенным переходом от MVP к полноценной SaaS-платформе. Главный принцип: **не ломать существующую архитектуру**, а наращивать функционал модульно.

---

## Этап 1: Фундамент и первые данные (2-3 недели)
**Цель:** Превратить заглушки в работающий прототип с реальными данными.

### 1.1. Инфраструктура и Безопасность
- [ ] **Настройка CI/CD**: Добавить GitHub Actions для автотестов и деплоя.
- [ ] **Production Docker**: Оптимизировать образы (multi-stage), добавить `docker-compose.prod.yml`.
- [ ] **Управление секретами**: Вынести токены и пароли в `.env`, настроить валидацию при старте.
- [ ] **Логирование**: Подключить структурированное логирование (Winston/Pino) с уровнями debug/info/error.

### 1.2. Работа с Wildberries (Приоритет №1)
- [ ] **Реальный клиент WB**: Заменить моки на вызовы API Statistics и Content.
- [ ] **Первый синк**: Реализовать ручную триггер-загрузку данных за последние 7 дней.
- [ ] **Валидация данных**: Проверка схемы ответов WB, обработка ошибок API (лимиты, таймауты).
- [ ] **Хранение токенов**: Шифрование токенов поставщиков в БД.

### 1.3. Telegram Интеграция
- [ ] **Бот-скелет**: Поднять вебхук, реализовать команды `/start`, `/help`.
- [ ] **Привязка магазина**: Механизм связи Telegram ID пользователя и магазина в БД.
- [ ] **Уведомления**: Отправка ежедневного отчета "Продажи за вчера".

### 1.4. База Данных
- [ ] **Миграции**: Настроить автоматическое применение миграций Drizzle при старте.
- [ ] **Индексы**: Добавить индексы на часто используемые поля (date, shop_id, article).

---

## Этап 2: Аналитика и Автоматизация (1 месяц)
**Цель:** Предоставить пользователю ценность через графики и авто-действия.

### 2.1. Расширенная Аналитика
- [ ] **Агрегация данных**: Cron-джобы для почасовой/дневной агрегации статистики (чтобы не считать "на лету").
- [ ] **Графики**: Внедрить Chart.js/Recharts на фронтенд (динамика продаж, воронка).
- [ ] **Юнит-экономика**: Расчет маржинальности по товарам (требуется ввод закупочных цен).
- [ ] **SEO Анализ**: Выгрузка поисковых запросов, анализ позиций карточек.

### 2.2. Умные уведомления
- [ ] **Триггеры**: Алерт при падении продаж >20%, при появлении негативного отзыва.
- [ ] **Остатки**: Уведомление о выкупах и остатках на складах WB.

### 2.3. Управление контентом
- [ ] **Загрузка фото**: Возможность менять фото товара через интерфейс.
- [ ] **Генерация описаний**: Интеграция с LLM (AI) для написания SEO-текстов.

---

## Этап 3: Мультипользовательность и SaaS (2-3 месяца)
**Цель:** Подготовка к продаже сервиса сторонним клиентам.

### 3.1. Архитектура Мульти-тенантности
- [ ] **Изоляция данных**: Строгий контроль доступа (RLS в БД или фильтрация на уровне репозитория).
- [ ] **Ролевая модель**: Admin, Manager, Viewer (разные права на чтение/запись).
- [ ] **Аутентификация**: JWT + Refresh tokens, восстановление пароля, 2FA.

### 3.2. Монетизация
- [ ] **Тарифы**: Ограничение функционала в зависимости от подписки (Free, Pro, Business).
- [ ] **Платежи**: Интеграция платежного шлюза (Stripe/CloudPayments/YooKassa).
- [ ] **Лимиты**: Очереди задач (BullMQ/Redis) для контроля нагрузки от разных тарифов.

### 3.3. Масштабирование
- [ ] **Кэширование**: Redis для кэширования частых запросов к API WB и тяжелых отчетов.
- [ ] **Микросервисы (опционально)**: Вынос тяжелых расчетов в отдельные воркеры.

---

## Этап 4: Экосистема и AI (3+ месяца)
**Цель:** Превращение в незаменимый инструмент.

- [ ] **Поддержка других маркетплейсов**: Ozon, Яндекс.Маркет (абстрактный интерфейс поставщика).
- [ ] **Предиктивная аналитика**: Прогноз продаж на основе ML, рекомендация товаров для закупки.
- [ ] **Авто-биддер**: Управление ставками в рекламе WB.
- [ ] **Публичное API**: Для интеграции с внешними системами (ERP, 1C).

---

## Технические долги и Риски (Работать параллельно)

| Риск | Решение |
| :--- | :--- |
| **API Лимиты WB** | Реализовать умную очередь запросов с приоритетами. |
| **Рост БД** | Партиционирование таблиц по датам, архивация старых данных. |
| **Сложность тестов** | Внедрить e2e тесты (Playwright) для критических путей. |
| **Безопасность** | Регулярный аудит зависимостей (npm audit), сканирование образов. |

## Рекомендации по внедрению
1. **Ветвление**: Каждую фичу делать в отдельной ветке `feature/name`.
2. **Code Review**: Обязательный ревью кода перед мерджем в `main`.
3. **Деплой**: Сначала на staging-окружение, прогон автотестов, потом прод.
4. **Документация**: Вести changelog и обновлять Swagger/OpenAPI спецификацию.
