## 🔧 Технические улучшения

### 1. Инфраструктура и DevOps

#### 1.1 Активировать CI/CD
**Приоритет:** Высокий  
**Сложность:** Низкая  
**Оценка:** 0.5 дня

```bash
mkdir -p .github/workflows && git mv docs/ci.workflow.yml .github/workflows/ci.yml
```

**Преимущества:**
- Автоматическая проверка типов и сборки
- Контроль миграций БД
- Раннее обнаружение проблем

#### 1.2 Добавить Dockerfile для продакшена
**Приоритет:** Средний  
**Сложность:** Низкая  
**Оценка:** 0.5 дня

Создать многоэтапный Dockerfile:
- Stage 1: сборка фронтенда
- Stage 2: сборка сервера
- Stage 3: минимальный runtime образ

**Преимущества:**
- Воспроизводимый деплой
- Меньший размер образа
- Безопасность (никаких dev-зависимостей)

#### 1.3 Настроить логирование для продакшена
**Приоритет:** Средний  
**Сложность:** Низкая  
**Оценка:** 0.5 дня

Текущее: `pino` с выводом в stdout  
Улучшения:
- JSON-формат для структурированного логирования
- Rotation логов через `pino-roll` или systemd-journald
- Корреляция запросов (request ID)
- Отдельный уровень для аудита действий

#### 1.4 Health checks для Kubernetes/Cloud
**Приоритет:** Средний  
**Сложность:** Низкая  
**Оценка:** 0.5 дня

Добавить эндпоинты:
- `/health/live` — процесс жив
- `/health/ready` — готов принимать трафик (БД, кэш подключены)
- `/health/deep` — глубокая проверка (токены площадок, лимиты)

### 3. Масштабирование

#### 3.1 Redis для лимитеров и сессий
**Приоритет:** Высокий  
**Сложность:** Средняя  
**Оценка:** 1-2 дня

Текущая проблема: лимитеры в памяти процесса умножаются на число инстансов

План:
1. Раскомментировать Redis в docker-compose
2. Перенести `rateLimiter.ts` на Redis (ioredis)
3. Сессии Telegram-пользователей в Redis
4. Кэш частых запросов к БД

**Миграция:**
- Feature flag `USE_REDIS`
- Деградация в memory при недоступности Redis

#### 3.2 Выделенный воркер синхронизации
**Приоритет:** Средний  
**Сложность:** Средняя

Решение:

- Graceful shutdown с завершением текущей задачи
- Метрики выполнения задач

#### 3.3 Очереди для массовых операций

### 4. Безопасность

#### 4.1 Аутентификация и авторизация
**Приоритет:** Критический (до первого пользователя)  
**Сложность:** Высокая  
**Оценка:** 3-5 дней

Необходимо до этапа 7 ROADMAP:
- JWT или session-based аутентификация
- Роли: owner / admin / operator / viewer
- Проверка `organization_id` в каждом запросе
- Rate limiting на публичных эндпоинтах

Варианты:
- Свой на Passport.js
- Auth0 / Clerk / Supabase Auth

#### 4.2 Ротация ключей шифрования
**Приоритет:** Средний  
**Сложность:** Средняя  
**Оценка:** 1 день

Текущее: один `SECRETS_ENCRYPTION_KEY`, смена ломает старые данные

Улучшение:
- Версионирование ключей (префикс в шифротексте уже есть)
-_endpoint для перешифрования старых записей новым ключом
- HSM или cloud KMS для продакшена

#### 4.3 Аудит безопасности
**Приоритет:** Высокий  
**Сложность:** Средняя  
**Оценка:** 2-3 дня

Проверить:
- SQL injection (Drizzle ORM защищает)
- XSS (React экранирует, проверить dangerouslySetInnerHTML)
- CSRF для веб-форм
- Secrets leakage в логах (уже есть маскирование)
- Rate limiting на чувствительных эндпоинтах
