# Подключение Wildberries

Пошаговый план на день подключения. Всё, что ниже помечено **VERIFY**, собрано
по памяти о публичной документации и не проверено запросами — сверить с
<https://dev.wildberries.ru> до первого боевого вызова.

## Шаг 1. Получить токен

1. Личный кабинет продавца → Настройки → Доступ к API → создать токен.
2. Отметить категории, которые нужны на первом этапе:
   - **Контент** — карточки товаров;
   - **Цены и скидки** — текущие цены (и позже их изменение);
   - **Статистика** — заказы, продажи, остатки FBO;
   - **Вопросы и отзывы** — отзывы;
   - **Маркетплейс** — склады и остатки FBS (нужно только при работе по FBS).
3. **Не выдавать токен «только на чтение»?** — WB не разделяет чтение и запись
   внутри категории. Поэтому защита от случайной записи у нас своя:
   `ALLOW_MARKETPLACE_WRITES=false` (см. `docs/ARCHITECTURE.md` → «Безопасные действия»).
4. Токен — это JWT-строка. Она даёт полный доступ к магазину: в git, в чат и в
   логи не попадает. Для разовой проверки кладётся в переменную окружения.

## Шаг 2. Проверить токен, ничего не меняя

```bash
MARKETPLACE=wildberries WB_TEST_TOKEN=<токен> npm run check:connection
```

Скрипт делает `/ping` и запрос имени продавца. Ожидаемый вывод — `Результат: OK`
и название аккаунта: это подтверждает, что токен от нужного магазина.

Токен читается из переменной окружения, а не из аргументов команды: аргументы
видны в списке процессов и остаются в истории shell.

## Шаг 3. Сверить карту эндпоинтов

Файл `server/connectors/wildberries/endpoints.ts`. У каждого пути стоит
`verified: false`. Порядок работы: открыть документацию, сверить хост, путь,
метод и лимит, поправить при расхождении, поставить `verified: true`.

Непроверенные пути перечисляются в логе при старте и в
`GET /api/platform/health` → `warnings.unverifiedWbEndpoints` — забыть не получится.

Что именно сверять:

| Что | Почему это ловушка |
|---|---|
| Хост группы API | WB переносил методы между `suppliers-api`, `content-api`, `discounts-prices-api`. Старые хосты какое-то время отвечают, потом отключаются |
| Версия пути (`v1`/`v2`/`v3`) | Разные группы живут в разных версиях одновременно |
| Формат заголовка авторизации | **VERIFY**: сейчас в коде `Authorization: <токен>` без префикса `Bearer` |
| Лимит запросов | Считается на группу API и на токен. У статистики он крайне жёсткий — **VERIFY**, порядка одного запроса в минуту |
| Пагинация карточек | Курсорная, курсор составной (`updatedAt` + `nmID`), а не номер страницы |

## Шаг 4. Реализовать чтение

Порядок важен: от самого дешёвого по лимитам к самому дорогому.

1. `listProducts` — карточки. Проверка: число карточек совпадает с личным кабинетом.
2. `listStocks` — остатки. FBO берутся из группы статистики, FBS — по каждому
   складу отдельно. Это два разных источника, не перепутать.
3. `listOrders` — заказы и продажи. Группа статистики, самый жёсткий лимит:
   ходить фоновым воркером, не из HTTP-запроса.
4. `listReviews` — отзывы.
5. `getSearchPositions` — отчёт по поисковым запросам заказывается асинхронно:
   сначала запрос на формирование, потом опрос готовности.

Каждый метод возвращает нормализованные типы из `server/connectors/types.ts`.
Цены с площадки приходят в рублях числом — переводить через `fromMajor(value, 'RUB')`,
чтобы в системе они лежали в копейках.

Критерий готовности этапа: сутки чтения на боевом токене без ошибок в логе.

## Шаг 5. Только потом — запись

`updatePrices`, `updateStocks`, `replyToReview`.

Обязательные условия до первого боевого вызова:

- проверка `ctx.allowWrites`;
- запись в `action_audit` со значениями «до» — до вызова API, не после;
- подтверждение оператора в интерфейсе или боте;
- прогон через `dryRun` на реальных данных.

Установка цен у WB асинхронная: метод возвращает идентификатор задачи, результат
опрашивается отдельно. Считать запись успешной по коду 200 нельзя — цена может
быть отклонена уже после приёма задачи.

## Типичные грабли

- **Цена и скидка — разные поля.** Покупатель видит цену со скидкой; менять
  только цену, забыв про скидку, — значит получить не тот результат, что ожидали.
- **Один товар — несколько размеров** со своими баркодами и остатками. Наша
  модель `NormalizedProduct` пока плоская: если магазин торгует размерными
  линейками, здесь понадобится сущность варианта.
- **FBO и FBS живут в разных API.** Остатки на складе WB и на складе продавца
  нельзя складывать без разделения по `fulfillment`.
- **Возвраты приходят в продажах отрицательными записями.** Считать выручку
  простой суммой — завысить её.
- **Пустой ответ при пустых правах.** Если категория не отмечена при выпуске
  токена, часть методов отвечает не 403, а пустым списком. Отсюда требование
  проверять `testConnection` и права до синхронизации.

## Ozon, Shopify, Китай

Коннекторы зарегистрированы заглушками (`server/connectors/registry.ts`), чтобы
интерфейс честно показывал «не подключено». Отличия, которые уже известны:

- **Ozon** требует пару `Client-Id` + `Api-Key` — кладётся в `credentials.extra`.
- **Shopify** — GraphQL с бюджетом стоимости запроса вместо счётчика запросов;
  лимитер под него нужен другой.
- **1688 / Taobao / JD** — это закупка, а не продажа: у них другой домен данных
  (фабрики, партии, MOQ), и класть их в тот же `MarketplaceConnector` скорее
  всего неправильно. Решать при подходе к этапу 6.
