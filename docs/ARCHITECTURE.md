# Архитектура CommerceOS

Документ описывает целевое устройство системы и то, что уже есть в коде.
Статус на 2026-09-06: работает демо-интерфейс на захардкоженных данных плюс
каркас backend-слоя. Ни один маркетплейс ещё не подключён.

## Что есть сейчас

| Слой | Состояние |
|---|---|
| Фронтенд `src/` (~26 тыс. строк, 40+ компонентов) | Работает. Данные — `src/data/mockStore.ts`, захардкожены |
| `server.ts` | 4 эндпоинта реально ходят в Gemini; остальные возвращают константы |
| Ядро `server/core/` | Готово, покрыто тестами (деньги, шифрование, лимитер, HTTP-ретраи) |
| Коннектор WB | Чтение написано (карточки, цены, остатки FBO, заказы, отзывы), **не проверено боевым токеном**. Запись и позиции в поиске — `NotImplementedError` |
| Хранилище | Схема, миграции, репозитории с идемпотентным upsert. **Покрыто интеграционными тестами на живой базе** |
| Синхронизация | Очередь на `SKIP LOCKED`, воркер и планировщик написаны, вживую не гонялись |
| Расчёт показателей | Готов, покрыт тестами: выручка, сравнение периодов, запас дней, кто просел |
| Диагностика и алерты | Правила написаны и покрыты тестами; доставка в Telegram с подавлением повторов |
| Telegram | Бот поднимается; `/digest`, `/sales`, `/stocks`, `/problems`, `/reviews`, `/stores`, `/sync` считают по БД, привязка через одноразовый код |

Что означает «не проверено»: формы ответов и большинство путей WB взяты
из документации по памяти, помечены `verified: false` и перечисляются
в `/api/platform/health`. Боевого токена не было, поэтому синхронизация вживую
не гонялась.

Слой данных, наоборот, проверен по-настоящему: 24 интеграционных теста на живом
Postgres плюс сквозной прогон `npm run smoke:db`. Первый же такой прогон нашёл
две ошибки, которых не видели ни компилятор, ни модульные тесты — раздел
«Что нашлось при первом запуске».

Демо-эндпоинты из `server.ts` намеренно не тронуты: интерфейс продолжает
работать, пока идёт подключение реальных источников. Удаляются они на этапе 3
дорожной карты, когда данные пойдут из БД.

## Слои

```
Telegram-бот ─┐
Веб-интерфейс ─┼─→ Сервисный слой ─→ Коннекторы ─→ API маркетплейсов
AI-оркестратор ┘         │
                         └─→ PostgreSQL (нормализованные данные, аудит, события)
```

**Правило зависимости:** стрелки идут только вправо и вниз. Коннектор не знает
про Telegram, бот не знает про WB. Всё общение — через нормализованные типы
`server/connectors/types.ts`.

### 1. Коннекторы — `server/connectors/`

Главный шов проекта. Интерфейс `MarketplaceConnector` описывает то, что умеет
любая площадка: список товаров, остатки, заказы, отзывы, позиции, реклама,
запись цен и остатков.

Почему так:

- Проект международный. WB, Ozon, Shopify, 1688 отдают несовместимые форматы,
  разные валюты, разные схемы фулфилмента. Если эта разница протечёт выше
  коннектора, она расползётся по всему коду и каждая новая площадка будет стоить
  переписывания UI.
- Добавление площадки = новый файл + строчка в `registry.ts`. Ни бот, ни
  дашборд при этом не меняются.
- Площадка чего-то не умеет — это флаг в `capabilities`, а не тихо возвращённый
  пустой массив. Пустой массив выглядит как «данных нет» и уводит отладку в сторону.

Нормализация:

- деньги — целые минорные единицы + ISO-код валюты (`server/core/money.ts`),
  никаких float;
- время — ISO-8601 в UTC; локальные сутки магазина считаются по `stores.timezone`
  (витрина в Китае и витрина в Москве закрывают сутки в разное время);
- идентификатор площадки хранится в `externalId`, внутренний UUID появляется
  только в БД;
- исходный ответ площадки кладётся в `raw` — помогает при отладке и позволяет
  достать поле, которое ещё не вынесли в колонку.

### 2. Транспорт — `server/core/http.ts`

Весь трафик к внешним API идёт через один `httpJson`: таймаут, ретраи с
экспоненциальной задержкой и джиттером, уважение `Retry-After`, единая
классификация HTTP-статусов в коды ошибок.

Лимитер (`server/core/rateLimiter.ts`) — token bucket на пару
**(магазин, группа API)**, а не один на процесс: WB считает лимиты отдельно по
каждой группе и на каждый токен продавца. Ограничение текущей реализации —
состояние в памяти процесса; при нескольких инстансах лимит умножается на их
число. Переносится в Redis на этапе 3.

### 3. Хранилище — `server/db/`

PostgreSQL + Drizzle. Схема — `server/db/schema.ts`, миграции коммитятся в git
(прод не обновляет схему через `push`).

Ключевые решения:

- **Multi-tenant по `organization_id`.** Он есть в каждой доменной таблице.
  Запрос без фильтра по нему — баг, ведущий к утечке чужих данных.
- **Секреты отдельной таблицей** `store_credentials`, зашифрованы AES-256-GCM
  (`server/core/crypto.ts`). Токен WB даёт полный доступ к чужому магазину,
  включая цены и поставки: дамп БД не должен означать компрометацию всех клиентов.
  Ключ — `SECRETS_ENCRYPTION_KEY`, версия алгоритма в префиксе шифротекста,
  чтобы можно было сменить алгоритм и дочитать старые записи.
  **Ротация ключа:** шифруем текущим, читаем текущим либо предыдущим
  (`SECRETS_ENCRYPTION_KEY_PREVIOUS`), перешифровка — `npm run rotate:key -- --apply`
  одной транзакцией. Идентификатор ключа в шифротексте не хранится намеренно:
  тег аутентичности GCM и так делает подбор однозначным — с чужим ключом
  расшифровка падает, а не выдаёт правдоподобный мусор.
- **Деньги в `*_minor` + колонка валюты.** RUB, CNY, USD лежат в одной таблице.
- **`action_audit` пишется до вызова API и обновляется после.** Иначе при падении
  процесса останется изменённая на маркетплейсе цена без следа о том, кто её поставил.

### 4. Telegram — `server/telegram/`

grammY. Два режима: `polling` для разработки, `webhook` для прода. Один токен в
двух процессах с polling конфликтует — поэтому режим задаётся явно, а не
угадывается.

Вебхук проверяет секрет из заголовка `X-Telegram-Bot-Api-Secret-Token` до разбора
тела: эндпоинт публичный, без проверки боту можно слать фальшивые апдейты.

Настройки пользователя сейчас в памяти процесса (`state.ts`) — заглушка на период
без БД. Интерфейс функций совпадает с будущим сервисным слоем, замена — одна.

### 5. Интернационализация — `server/i18n/`

Ни одна пользовательская строка не пишется в коде: только ключ + каталог.
Русский каталог эталонный, его набор ключей задаёт тип `MessageKey`, поэтому
забытый ключ в другом языке падает на типах, а не в проде.

Локаль определяется: сохранённая настройка → язык клиента Telegram → `DEFAULT_LOCALE`.

## Счёт показателей

`server/analytics/metrics.ts` — чистые функции без сети и без БД. Языковой модели
счёт не доверяется: её дело сформулировать, а не посчитать. Выборки из БД лежат
отдельно (`db/repositories/analytics.ts`), потому что считать в SQL значит
не иметь возможности проверить расчёт без поднятой базы.

Решения, которые легко сделать неправильно и которые зафиксированы тестами:

- отменённые и возвращённые заказы не выручка;
- заказ из трёх позиций — один заказ, а не три; выручка при этом складывается
  по позициям;
- процент от нулевой базы — не «+∞» и не «0%», а честное «сравнить не с чем»;
- сутки считаются в таймзоне магазина: у витрины в Москве и в Гуанчжоу «вчера»
  разное;
- скорость продаж берётся за две недели, а не за сутки: суточная слишком шумная
  для оценки запаса;
- нулевой остаток — «закончился», а остаток без продаж — «неизвестно», а не
  «всё хорошо»: второе было бы неправдой;
- «кто просел» сортируется по абсолютной сумме, а не по процентам — товар,
  проданный один раз вместо двух, даёт -50%, но магазину это безразлично.

## Диагностика и алерты

Обе подсистемы устроены одинаково: правила — чистые функции над фактами,
выборка и доставка — этажом выше. Причины просадки считает код; модель может
пересказать вывод, но не придумать его — придуманные причины она выдаёт
убедительно и неверно.

Диагностика проверяет по порядку: закончился ли товар, вырос ли фактический
чек, появился ли свежий негатив, всплеск ли отмен, и не размазано ли падение
по всему ассортименту. Гипотезы, для которых нет источника данных (позиции
в поиске, цены конкурентов), не выдумываются — они перечисляются как
непроверенные, и по этому списку видно, чего не хватает.

Объяснённой считается только та часть падения, под которую нашлась внятная
причина. «Просел спрос» в объяснённое не входит: это констатация падения
другими словами.

Алерты подавляются по ключу на 12 часов. Одна и та же проблема, приходящая
каждые полчаса, заканчивается отключёнными уведомлениями и пропущенной
настоящей бедой. Событие пишется до отправки: пропустить одно уведомление
дешевле, чем слать его по кругу. Блокировка бота получателем выключает ему
рассылку, а не считается сбоем.

## Развёртывание

Образ двухстадийный: в первой ставятся все зависимости и идёт сборка,
во вторую переносится только собранное плюс продакшен-зависимости. Vite,
esbuild и typescript в рантайм не попадают.

Миграции применяет сам контейнер при старте — но **не** через `drizzle-kit`:
это dev-зависимость, в рантайм-образе её нет и быть не должно. Мигратор
`server/scripts/migrate.ts` собран в `dist/migrate.cjs` и использует
`drizzle-orm/node-postgres/migrator`, который и так в продакшен-зависимостях.

Ожидание базы конечное и только на ошибках соединения: бесконечный цикл вокруг
миграции превратил бы сломанный SQL в вечное «жду базу». Неудачная миграция
останавливает запуск — сервис не должен подниматься на схеме, которой
не соответствует код.

Процесс идёт под `tini` и не от root. Без init-процесса Node получает PID 1
и не обрабатывает SIGTERM, из-за чего graceful shutdown (остановка воркера
и бота) не срабатывает.

## Что нашлось при первом запуске

Две вещи, которые не ловились ни типами, ни тестами на фикстурах.

**Умерший товар был не виден при ровном магазине.** Диагностика запускалась
только при падении выручки магазина больше чем на 10%. В прогоне один товар
кончился совсем, другой вырос и закрыл дыру — общая просадка вышла 8.7%,
и разбор ответил «просадки нет». Это ровно тот случай, ради которого продавец
и подключает сервис. Теперь разбор запускается ещё и когда один товар потерял
пятую часть прошлой выручки магазина. Заодно вклад товара считается от валового
падения, а не от общей дельты: при выросшем магазине она положительна,
и деление уходило в бессмыслицу.

**`/ping` у WB отвечает 401, а не 200.** Проверка токена звала `/ping` как
проверку живости и на любую ошибку писала «WB API не ответил, проверь сеть» —
то есть врала про недоступный хост, когда на самом деле не подошёл токен.
Теперь проба различает три исхода: хост молчит, хост отвечает и токен не принят,
токен принят.

## Вход и права

Сессии в таблице, не JWT. Сессию можно отозвать: при смене пароля, при
увольнении сотрудника, при подозрении на утечку. Отозвать выданный JWT без
такой же таблицы нельзя, и «stateless» превращается в «неотзываемый».

В базе лежит SHA-256 токена, а не сам токен — та же логика, что и с токенами
площадок: дамп базы не должен давать возможность войти под чужой сессией.

Пароли — scrypt из стандартной библиотеки. Параметры записаны в самой строке
хеша, поэтому их можно поднять, не ломая существующие пароли: старые проверятся
своими, новые — новыми, а при входе запись тихо перехешируется.

Что сделано против перебора и разведки:

- ответ на неверный пароль и на несуществующую почту одинаковый, иначе
  перебором собирается список зарегистрированных адресов;
- проверка хеша выполняется даже когда пользователя нет — быстрый ответ
  выдавал бы отсутствие аккаунта;
- ограничение частоты по почте и по адресу, отдельно от общего лимита;
- за nginx включается `trust proxy`, иначе `req.ip` равен адресу прокси
  и лимит считается на один ключ для всех.

**Организация берётся только из сессии.** Раньше роуты принимали
`organizationId` в теле запроса — именно поэтому их приходилось выключать
в production. Теперь подделать нечего: идентификатор приходит из `memberships`
по токену. Роли: `viewer` < `operator` < `admin` < `owner`; подключение
магазина требует `admin`, потому что сохраняемый токен площадки даёт полный
доступ к чужому магазину.

Кука `httpOnly`, `SameSite=Lax`, `secure` только в production. Дополнительно
изменяющие запросы требуют `Content-Type: application/json`: форма с чужого
домена не может отправить такой заголовок без CORS.

## Страница настройки

`/setup` — вход, подключение магазина, состояние установки. Отдельно
от демо-SPA и намеренно без сборки:

- демо работает на захардкоженных данных, и подключение настоящего магазина
  внутри него смешало бы выдуманные цифры с реальными;
- страница нужна в том числе когда всё остальное сломано, поэтому не должна
  зависеть от сборки фронтенда;
- разметка встроена в код, а не читается с диска: в образ копируется только
  `dist`, лишний файл пришлось бы тащить отдельно.

Внешних ресурсов не тянет, CSP запрещает всё, кроме своего источника.
Скрипт страницы компилятор не проверяет, поэтому его синтаксис проверяется
тестом — сломанная кавычка иначе видна только в браузере и только по пустой
странице.

## Ревизия 06.09.2026: что нашлось и как закрыто

Разбор собственного кода после того, как основные подсистемы сошлись вместе.
Восемь проблем, все подтверждены до правки.

**Демо-эндпоинты с Gemini были открыты наружу.** `/api/chat` и три `/api/generate-*`
ходят в платный API на каждый запрос. На публичном адресе это чужой счёт за наш
ключ. Теперь: ограничение частоты всегда, в production — обязательный вход.
В разработке демо продолжает работать без входа.

**`/api/platform/rate-limits` светил идентификаторы магазинов.** Ключи лимитеров
имеют вид `wb:<storeId>:<группа>`, то есть аноним получал список арендаторов
установки. Закрыт входом, как и `/connectors`.

**Health отдавал карту установки.** Имена незаданных переменных, список
несверенных путей WB, число пользователей бота, причину недоступности базы
(в ней бывает строка подключения). Осталось публичным только то, что нужно
healthcheck контейнера и странице `/setup` до входа: булевы признаки готовности.

**Остаток исчезнувшего склада жил вечно.** `distinct on` без ограничения
по времени брал последний известный снимок, даже если площадка перестала
отдавать этот склад. Остаток выглядел завышенным, запас дней большим —
и алерт об окончании товара не сработал бы. Ровно тот случай, ради которого
всё и делалось. Теперь снимки старше трёх суток в расчёт не идут.

**Алерты считались четыре раза за цикл, на полусинхронизированных данных.**
Они запускались после каждого модуля: остатки уже свежие, заказы ещё
вчерашние — и запас дней выходил неверным. Теперь один раз, когда по магазину
не осталось задач в очереди.

**Лимит попыток входа был неатомарным и тёк.** Использовался token bucket,
рассчитанный на ожидание: проверка и списание шли двумя шагами, брошенный
`acquire()` оставлял висеть промис, а словарь лимитеров рос без ограничения —
ключ берётся из запроса, то есть память съедалась чужими данными. Заменён
на счётчик с окном, отказом и потолком ключей (`server/core/attemptLimiter.ts`).

**Кривая кука роняла запрос в 500.** `decodeURIComponent('%')` бросает
`URIError`; сделать это можно было одним запросом. Теперь значение отдаётся
как есть.

**Словари в памяти росли без уборки** — лимитер по адресу и отметки активности
сессий. У обоих появился потолок.

## Безопасные действия

Запись в маркетплейс (цены, остатки, ответы на отзывы) проходит три ворот:

1. `ALLOW_MARKETPLACE_WRITES` в окружении — общий рубильник;
2. `ConnectorContext.allowWrites` — право конкретного вызова;
3. запись в `action_audit` со снимком значений «до» — основа для отката.

`WriteResult.dryRun` позволяет прогнать сценарий целиком, ничего не отправив
на площадку. По умолчанию система read-only: сначала сутки чтения на боевом
токене, потом запись.

## Очередь и воркер синхронизации

Синхронизация с маркетплейсом — фоновая задача, а не HTTP-запрос: у WB группа
статистики отдаёт примерно один запрос в минуту, полный обход каталога занимает
минуты. Пользователь не должен ждать этого в браузере, а таймаут прокси не должен
ронять синхронизацию.

Очередь — таблица `sync_jobs`, задача забирается через
`SELECT ... FOR UPDATE SKIP LOCKED`: два воркера не подерутся за одну строку.
Отдельный брокер (RabbitMQ, Redis Streams) на нашем объёме не даёт ничего сверх
этого, а инфраструктуру усложняет.

Воркер (`server/sync/worker.ts`) работает последовательно, по одной задаче:
параллелизм не ускорит — упрёмся в лимиты площадки, зато усложнит отладку.
Зависшие задачи (воркер упал между «взял» и «завершил») возвращаются в очередь
по таймауту, иначе модуль перестанет обновляться молча.

Сейчас воркер живёт в том же процессе, что и веб. Когда инстансов станет больше
одного, он выносится отдельно — очередь это уже позволяет. Тогда же появляется
Redis для общих между инстансами лимитеров.

Идемпотентность: всё пишется upsert'ом по `(store_id, external_id)`, повторный
проход не плодит дубли. Исключение — остатки: это снимки во времени, они всегда
добавляются, иначе не посчитать скорость расхода.

## Тесты

`npm test` — встроенный `node:test`, без дополнительного раннера.

Покрыто то, где ошибки тихие и дорогие: арифметика денег, шифрование секретов
и ротация ключа, лимитер, ретраи HTTP, нормализация ответов WB, обход страниц,
расчёт показателей, диагностика, алерты. Компоненты интерфейса не покрыты
сознательно — они переписываются вместе с переходом на реальные данные.

**Интеграционные тесты** (`server/db/**/*.test.ts`) работают на живом Postgres:
SQL компилятор не проверяет, а ошибка в имени колонки или забытый фильтр
по организации всплывают только при выполнении запроса. Изоляция — своя
организация на каждый тест с каскадным удалением в `finally`; откат транзакции
не годится, потому что репозитории берут соединение сами. Без `DATABASE_URL`
эти тесты пропускаются: разработчик без Postgres не должен получать красную
сборку из-за отсутствия инфраструктуры, но в CI база есть всегда.

Отдельно проверяется изоляция арендаторов: забытый фильтр по `organization_id` —
это не просто баг, а чужие продажи в чужом отчёте.

Важно понимать границу: тесты нормализации проверяют **нашу** логику приведения
к общим типам на фикстурах ожидаемой формы. Они не подтверждают, что WB отдаёт
именно такую форму — это проверяется только боевым токеном.

## Чего осознанно нет

- **Приглашений в организацию.** Регистрация всегда заводит новую организацию;
  добавить второго человека в существующую пока нельзя. Роли и проверки прав
  для этого уже готовы.
- **Восстановления пароля.** Нужна отправка почты, которой в проекте нет.
- **Интеграционных тестов с БД.** На машине разработки не было Postgres;
  репозитории и воркер проверены только типами. Первый запуск с живой базой —
  этап 1 дорожной карты.
- **Своего слоя AI-агентов.** Сейчас Gemini вызывается напрямую из `server.ts`
  на захардкоженных фактах. Когда данные пойдут из БД, вызов переезжает в
  сервисный слой, а факты собираются кодом — модель их только формулирует.
  Считать цифры моделью нельзя: она их придумывает.
