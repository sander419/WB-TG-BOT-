# Дорожная карта

Порядок выбран так, чтобы каждый этап заканчивался проверяемым результатом,
а не «половиной подсистемы». Оценки — в рабочих днях одного разработчика.

## Этап 0. Каркас — сделано (2026-09-05)

Конфиг с валидацией, таксономия ошибок, логи с маскированием секретов,
шифрование токенов, HTTP-клиент с ретраями, лимитер, схема БД + миграция,
контракт коннекторов, реестр площадок, Telegram-бот на grammY, i18n (ru/en),
docker-compose, CI.

Проверено: `npm run lint` и `npm run build` проходят, миграция генерируется.

## Этап 1. Инфраструктура на машине — 0.5 дня

- [ ] `docker compose up -d db`
- [ ] `npm run gen:key` → `SECRETS_ENCRYPTION_KEY` в `.env`
- [ ] `DATABASE_URL` в `.env`
- [ ] `npm run db:migrate`
- [ ] `GET /api/platform/health` → `database.ok: true`, `encryption.configured: true`

## Этап 2. Чтение из Wildberries — 3–5 дней

Подробности и грабли — `docs/INTEGRATION-WILDBERRIES.md`.

- [ ] Получить боевой токен, прогнать `npm run check:connection`
- [ ] Сверить все пути в `endpoints.ts` с документацией, снять `verified: false`
- [ ] Сервис магазинов: создание магазина, сохранение зашифрованного токена
- [ ] `listProducts` → запись в `products`
- [ ] `listStocks` → `stock_snapshots` (FBO и FBS — разные источники)
- [ ] `listOrders` → `orders` + `order_lines`
- [ ] `listReviews` → `reviews`
- [ ] Фоновый воркер синхронизации на `sync_jobs`

**Готово, когда:** сутки синхронизации на боевом токене без ошибок, числа в БД
сходятся с личным кабинетом продавца.

## Этап 3. Реальные данные вместо демо — 3–4 дня

- [ ] Сервисный слой: сводка за сутки, остатки, диагностика просадки — считает
      **код**, а не модель
- [ ] Заменить захардкоженные ответы в `server.ts` на запросы к БД
- [ ] `USE_MOCK_DATA=false`, фронтенд ходит в реальные эндпоинты
- [ ] Убрать демо-эндпоинты и `src/data/mockStore.ts`
- [ ] Команды бота `/digest`, `/sales`, `/stocks`, `/problems`, `/reviews`
- [ ] Привязка магазина к Telegram через одноразовый код
- [ ] Алерты: падение позиций, out-of-stock, демпинг, негативный отзыв
- [ ] Redis + общие лимитеры, если инстансов больше одного

**Готово, когда:** продавец видит в боте свои настоящие цифры за сутки.

## Этап 4. Запись в маркетплейс — 2–3 дня

- [ ] `action_audit` пишется до вызова API
- [ ] Подтверждение оператора в интерфейсе и в боте
- [ ] `updatePrices` с опросом статуса асинхронной задачи
- [ ] `updateStocks` (FBS)
- [ ] `replyToReview`
- [ ] Откат по снимку «до»

**Готово, когда:** цена меняется из бота с подтверждением, в аудите видно кто,
что и когда, и изменение откатывается одной командой.

## Этап 5. Ozon — 2–3 дня

Проверка контракта коннекторов на второй площадке. Если `MarketplaceConnector`
спроектирован верно, ни бот, ни UI не меняются. Если менять придётся — это
сигнал, что абстракция протекает; чинить сейчас, а не на пятой площадке.

- [ ] `Client-Id` + `Api-Key` в `credentials.extra`
- [ ] Чтение: товары, остатки, заказы, отзывы
- [ ] Мультивалютность на реальных данных

- [ ] Деплой на VPS: systemd или контейнер, миграции при выкатке

## Что решить до этапа 2

1. **Одна страна или сразу несколько.** От этого зависит, нужны ли юридические
   поля в схеме (НДС, режим налогообложения) уже сейчас.
2. **Размерные линейки WB.** Если магазин торгует размерами, нужна сущность
   варианта товара — это правка схемы, дешевле сделать до наполнения данными.
3. **Кто хозяин цены.** Меняет её только человек через подтверждение, или
   правило может менять автоматически в заданном коридоре. Ответ определяет
   объём этапа 4.
